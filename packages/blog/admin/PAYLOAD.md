# Payload CMS

[Payload](https://payloadcms.com/) is a headless CMS and application
framework that runs directly inside this Next.js app. One config file,
`payload.config.ts`, declares the content model (collections) and Payload
generates the admin UI (`/admin`), REST API (`/api/*`), and GraphQL API
(`/api/graphql`) from it. This app uses it store and manage all blog
related content.

## Collections

| Collection | Purpose                                                                                                                                                                                                                                                                      |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users`    | Admin authentication (`auth: true`) - gates access to `/admin` and to unpublished content. No content fields of its own.                                                                                                                                                     |
| `media`    | File uploads (images, etc.) - GCS-backed via the `gcsStorage` plugin when `GCS_MEDIA_BUCKET` is set, local disk otherwise. Used as the relation target for `posts.heroImage`.                                                                                                |
| `posts`    | The blog content `blog-website` reads. Draft/publish workflow (`versions.drafts`); anonymous requests only ever see published posts. A computed `contentHTML` field renders the Lexical `content` field to HTML, so `blog-website` never has to parse Lexical's JSON itself. |

## CLI commands

Every `payload` CLI command loads `payload.config.ts`, which has the
side effect of reading environment variables like `PAYLOAD_SECRET` - see
[RUNBOOK.md](./RUNBOOK.md). Locally, `.env` is loaded, so the command below
run with no extra setup.

### Update generated types and admin UI

Run either after any change to `payload.config.ts` or a file under
`src/collections/`:

```
npx payload generate:types
npx payload generate:importmap
```

### Migrations

```
npx payload migrate:create <name>  # after a schema change, to create a new migration
npx payload migrate                # apply pending migrations
npx payload migrate:status         # see what's applied vs. pending
npx payload migrate:down           # roll back the most recent migration
npx payload migrate:refresh        # roll back everything, then reapply
npx payload migrate:reset          # roll back everything, don't reapply
npx payload migrate:fresh          # drop everything and start over
```

`payload migrate` (no subcommand) is also what runs automatically in
production, before the server starts - see RUNBOOK.md's "Startup
sequence."

## Generated files

| File                                                      | Generated by            | Committed? | Regenerate when                                                                                                                                                                                                 |
| --------------------------------------------------------- | ----------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/app/admin/importMap.js`                              | `generate:importmap`    | Yes        | Any admin-UI-registering plugin/component/richtext feature is added, removed, or upgraded - a missing entry surfaces as a blank/broken admin page (see [known-issues.md](./known-issues.md))                    |
| `src/payload-types.ts`                                    | `generate:types`        | No         | Any collection/field is added, removed, or changed. `next dev` may regenerate this automatically on config changes; run explicitly to be sure (CI, after a fresh pull, before writing code against a new field) |
| `src/migrations/<timestamp>[_name].ts` + matching `.json` | `migrate:create <name>` | Yes        | Any collection/field change that needs to reach a real (non-dev) database - one pair per migration                                                                                                              |
| `src/migrations/index.ts`                                 | `migrate:create`        | Yes        | Automatic - `migrate:create` appends to it; never hand-edit                                                                                                                                                     |
| `src/payload-generated-schema.ts`                         | `generate:db-schema`    | N/A        | On demand only, for inspecting the current Drizzle/SQLite schema shape - not part of this project's regular workflow (`migrate:create` diffs the schema itself, without needing this file first)                |
